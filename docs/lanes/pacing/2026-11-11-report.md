**Conditions, for every number below.** M3 Pro, built-in 120 Hz panel, macOS 15. In-process probe
(`pace_probe`, the bough-awagy dashboard and scroll apps through `Application::run`, AWAGY's input schedule posted
to the app's own event queue). Every batch ran under the measurement lock, but other lanes kept building: the
1-minute load average was 50–105 throughout (each batch's range is in the results file). No number here was taken
on a quiet machine. Latency is "input → vsync after commit": from the event's own timestamp to the first vsync at or
after the end of the Core Animation commit that first shows it. Input-to-photon ≈ that + ~16.7 ms (two refreshes
through the window server, measured for CAMetalLayer with `presentedTime`; assumed, not measured, for bough's
IOSurface contents).

## 1. Frame log (F2 instrument)

Feature `framelog` of bough-metal/bough. Without it every mark is an empty `#[inline(always)]` body and costly
arguments sit behind a `const false`, so the default build is meant to compile to the same code. That was **not
checked with the instruction cells** (G5 not run). The log records per turn: the event time, dispatch, GPU sync,
settle, describe, layout, frame, pick, slot, end, CPU time and faults. Per publication it records post, take,
GPU-done and commit times, plus vsyncs (the host link, and a measurement CVDisplayLink) and notes for every stall
mechanism. Readers: `bench/pacing/{framelog,aggregate,gaps}.py`.

## 2. Stall diagnosis (F2)

The 75.7 ms AWAGY gap did not recur in ~120 in-process dashboard runs (35 of them frame-per-event). The worst A (frame-per-event) gaps were 129,
64, 43 and 34 ms, all under load 60–105. `gaps.py` attributes every commit gap ≥ 16.7 ms:

| build | gaps ≥ 16.7 ms | dominant mechanism |
|---|---|---|
| A, 15 runs (`ab1`, `abc1`) | 35 | main thread not scheduled while events queued (31); publisher wake (2); long turn (2) |
| B (X4 latch), 15 runs | 85 | main thread not scheduled (83) |
| C1 (deadline commit), 5 runs | 4 | main not scheduled (2); publisher (2, which includes its intended deadline sleep) |

The worst A gap (129 ms) had events queued 118 ms with no turn running, and the publisher 121 ms late: the whole
process was starved of CPU. bough's own turns are small: input turns p50 0.01–0.05 ms, p99 ≤ 1 ms. The mechanisms
the log shows inside bough, with the largest single cost observed:

* GPU sync before a turn writes the region: up to 24.7 ms under load.
* Ring exhaustion: all 4 surfaces held, the main thread sleeps; up to 6.4 ms in A at 240 presents/s, never in B or E.
* Residency drains: a surface's first use releases up to 16 pre-armed frames one GPU round trip at a time; 1.5–6.9 ms.
* Publisher wake at default QoS: up to 17 ms post-to-take under load.
* First frame after 1 s idle (GPU wake): 4–5 ms.
* **A real failure the trace led to.** After ~10 s without frames, the driver kills the waiting pre-armed batch
  (`kIOGPUCommandBufferCallbackErrorTimeout`), and the next frame panicked after 5 s. Fixed with a recovery path
  and gated by `tests/stall.rs`; the long-idle test failed before the fix and passes after. The requested 3 s
  SIGSTOP/SIGCONT test passes both before and after: while the process is stopped, nothing waits on the GPU.

Most likely cause of AWAGY's 75.7 ms: CPU starvation of the app's threads (the same signature at 34–129 ms here).
Not proven for that run.

**Scroll p95 mechanism (AWAGY 12.4 ms vs iced 8.4).** Input-animation frames were "paced": committed at the next
sync, which the next input event usually triggers (237 of 240 commits in one scroll phase). The commit cadence
therefore beat between the 144 Hz wheel and the 120 Hz link.

## 3. The compositor deadline (measured)

A present made 0.25–7 ms before the link's target T is shown at T + 2 refreshes (24/24 per phase). One made at the
callback (V + 0.3 ms) is mostly shown at T + 1. The window server takes commits up to ~0.3–1.3 ms after each vsync.
CVDisplayLink's `inNow` is its wake-up, 11.56 ms before `inOutputTime`; `inOutputTime` equals CADisplayLink's target
within 4 µs.

## 4. What was built and how it measured

* **X4 (display-paced input with a late latch).** An input queue that merges only adjacent moves and same-sign
  wheels, drained at run-loop before-waiting. A pacer: present at once when idle, else one latch at T − lead with
  an adaptive lead, input animations stepped at the latch. The publisher thread runs at user-interactive QoS.
  * Presents fell from 240 to 120/s.
  * Scroll improved strongly (`ab1`, input→vsync p50 6.2–8.8 vs A 12.7–13.0 ms).
  * Under load the latch timer fired 1.0–1.6 ms late at p50 and 3.6–4.4 at p99. So discrete input lost a refresh at
    p99 (typing/refresh/toggle p99 17.9–19.2 vs A 9.3–10.3), and ~3 % of refreshes got two commits.
  * **Fails its frozen latency threshold and G1's 1 % clause: REJECTED as the default.** Kept selectable
    (`BOUGH_PACE=latch`, frame-log builds).
* **Late latching (task 3).** X4's latch against drawing at the link callback (`latch1`, load ~62): discrete
  input→vsync p50 3.9–7.7 vs 11.0–13.1 ms, scroll 8.0 vs 13.4. Sampling at the latch saves most of a refresh
  without a second present, when the timer is on time.
* **Deadline commit (final default, "E").** The main thread draws as soon as input is drained. The publisher, on a
  time-constraint thread, commits at most once per refresh at T − 0.5 ms on the phase the host's link gives it. A
  burst is paced from its second frame. Variants v2 (hold-back), v3 (mailbox, exhausts the 4-surface ring) and D
  (animations at the latch) were measured worse and are recorded in the card.

## 6. Off-display windows (the lead's question)

A borderless window placed outside every display gets **no CADisplayLink callbacks at all**. `latch_cal` printed
nothing in 12 s, and the host never mounted, because it mounts on the first link tick. Display-paced pacing cannot
be measured off-display. The Space helper must be checked for the same property before any windowed measurement
resumes. The probe now defaults to off-display (`BOUGH_ONSCREEN` restores the old placement), so it does not run
until a placement that keeps the link alive exists.

## 7. ProMotion (F13)

The host's link already ran at 120 Hz by default: link callbacks 239–240 per 2 s in A's scroll phase. It now asks
for the screen's maximum explicitly. During scroll storms, B and E saw 119–120 refreshes/s, with link callbacks
matching the recorder's vsyncs. A per-source frame-rate range (lower for slow animations) was not built.
