# Card: the memory ledger (who holds every byte)

```
lane:            memory
state:           CARD
owner:           memory session, round 6 (one experiment, one owner)
predecessor:     aa9943e7ae (lead/round6-base); nightly-2026-10-17; release profile (debug=1, thin LTO);
                 direct Metal presenter (no `wgpu` feature)
question:        For the counter example, AWAGY dashboard, AWAGY scroll at 100 / 1 K / 7 K rows and the heavy
                 scene, which holder owns each byte of phys_footprint and of resident memory, and which of
                 those bytes scale with content (rows) and which with the window?
change:          Instrumentation only, off unless asked for:
                 * bough-mem: residency of any address range (mincore: resident and modified pages) and a
                   per-`Col` record (len, capacity, resident, dirty);
                 * an in-process ledger (`App::ledger`): every region column, the frame slots and header,
                   the CPU-side tables of bough-core / bough-text / the façade / the layout engine (Vec
                   capacities, mincore where an allocation spans whole pages), the text caches (atlas CPU
                   copy, strikes, font copies, shaping tables), and the presenter's GPU objects (surfaces
                   touched x bytes, atlas, bins, counts, image atlas, the region buffer) plus Metal's
                   `currentAllocatedSize`;
                 * a counting global allocator that harness binaries opt into (live Rust heap bytes and
                   allocation counts; the "debug allocator hook" of AUDIT R4);
                 * a harness entry (`Application::run_harness`) that runs a prelude view exactly as
                   `Application::run` does, plus a start hook and an exit timer, and a ledger timer in the
                   host (`BOUGH_LEDGER=<file>`, `BOUGH_LEDGER_AT=<s>`);
                 * `bench/memory/ledger.py`: launches each workload, samples proc_pid_rusage
                   (ri_phys_footprint, ri_resident_size), `footprint -j` (categories, dirty / clean /
                   swapped / wired), `vmmap --summary`, `heap -s` at the same moment the app writes its
                   ledger, and joins them into one table.
implication:     Passing gives a table whose named holders sum to the measured phys_footprint and RSS within
                 the stated residual, per workload, with the per-row slope from the three scroll sizes, and an
                 account of the RSS-vs-footprint gap. It does not establish anything about other machines,
                 display scales, or macOS versions, nor that a holder can be removed.
platforms:       macOS 15 (Darwin 24.6), M3 Pro, 36 GiB, built-in display at 2x; direct Metal.
workloads:       counter (crates/bough/examples/counter.rs's view); AWAGY scroll (comparisons/bough-awagy
                 scroll.rs, SCROLL_ROWS = 100, 1000, 7000) scrolled in-process at 120 Hz by the same
                 `App::wheel_points` path a wheel event takes (no synthetic global input); AWAGY dashboard
                 (dashboard.rs) scrolled the same way; heavy (zgx heavy, ZGX_MODE=both) windowed.
                 Windows: Accessory activation policy, `orderFrontRegardless` (no focus taken), closed by the
                 harness's exit timer.
gates:           Instrumentation must not change behaviour: the ledger and allocator code is not reachable
                 unless the env var / harness asks; `cargo test --release -p bough-mem -p bough` passes; the
                 instruction slopes of heavy stream/scroll, lab both, animate and vlist scroll stay within
                 1.02x of the base build (negative control: a build that calls the ledger every frame must
                 show up as a slope change, proving the slope method sees it).
                 Ledger self-check: sum of named holders vs phys_footprint, residual reported, never hidden.
thresholds:      Attribution target: named holders explain >= 95 % of phys_footprint on every workload; any
                 residual above 5 % is reported as such (not forced into a holder).
measurement:     3 runs per workload, sampled at t = 5 s (active scrolling) and again 3 s after scrolling
                 stops (calm, after the trim timer). Memory is not timing: the measurement lock is checked
                 before windowed runs (and held while they run, as they put load on the GPU and compositor).
budget:          one session-day; this Mac only.
stop conditions: if footprint attribution stays below 80 % after the driver probes, record METHOD_BOUNDARY
                 for the unexplained part with what was tried.
do not revisit:  SETTLED: present paths with commit costs (CAMetalLayer drawables etc.). Round 5's finding
                 that `maxCommandBufferCount`, hazard tracking, storage modes and plain textures do not move the
                 driver block (crates/bough/RESULTS.md 2.3) is re-checked only through the new probes, not
                 re-argued.
```
