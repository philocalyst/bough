Benchmark evaluation · areweactuallyguiyet.mespin.me workloads

bough on AWAGY

bough, run through the two workloads of Are we actually GUI yet? on this Mac, next to the site’s own two Vizia apps, built and measured here the same way, and next to two frameworks the site does not register, zgx and BUI (Blender’s UI as a library), measured here with the same protocol. The site's own collection was on Linux at 144 Hz and cannot include bough, so its numbers appear only as context.

Verdict

Against the site’s two Vizia apps, measured side by side: bough wins every scroll measure and most dashboard measures by a wide margin. It loses one dashboard result: the site’s headline number, because one of its three runs stalled once.

  • WinScroll at 7,000 rows:
    • presents per second: 120.0, the display’s limit, against 112.0 for Vizia (optimized) and 22.3 for Vizia;
    • p95 gap: 12.4 ms against 16.8 and 60.1 ms;
    • longest gap: 14.1 ms against 33.0 and 76.3 ms.
    At 1,000 rows all three sit near the display’s limit.
  • WinWork and memory:
    • CPU in the 3 s window at 7,000 rows: 121 ms against 1,369 ms (11×) and 8,626 ms (71×);
    • resident memory: 68 MiB against 438 and 441 MiB;
    • physical footprint, which also counts the GPU driver’s memory: 175 MiB against 435 and 430 MiB.
  • WinExecutable: 2.7 MiB against 18.7 and 18.8 MiB. bough loads its font from a file at run time; Vizia carries fonts in its binary.
  • WinDashboard, the rest:
    • p95 gap: 9.2 ms against 16.4 and 35.3 ms;
    • mean resident memory: 66 MiB against 160 and 164 MiB;
    • CPU: 2.1 s against 4.6 and 9.8 s over the 8 s workload.
  • LossDashboard worst gap, the site’s headline: the site keeps the worst gap across runs, which gives 75.7 ms for bough against 31.0 ms for Vizia (optimized). bough’s other two runs were 15.3 and 15.1 ms, lower than every Vizia run. The stall fell in the Refresh phase, and its cause has not been found.
  • EvenClicks counted (corrected): no click was dropped. In the run captured on screen (the one with the stall), bough’s counter shows 467, and the driver’s own record of that run (events_sent for the Refresh phase in results.json) is 467: the harness sent 467 Refresh clicks in that run, not 480, and bough counted every one. Its other two runs sent and counted 480. An earlier version of this page called this 13 dropped clicks; that was wrong.

Against zgx and BUI, measured side by side

zgx (Zeron, 0f0a08af, built as its getting-started guide says, with its patch set) and BUI (Blender’s UI as a standalone library, d6be0397), run through the same workloads, input and present observer. Medians of three runs.

  • WinScroll at 7,000 rows: 120.0 presents/s, p95 12.4 ms, longest gap 14.1 ms for bough against 111.3 / 16.7 / 25.0 for zgx and 21.0 / 68.9 / 170.8 for BUI. CPU in the 3 s window: 121 ms against 752 (6.2×) and 2,900 ms (24×); resident memory 68 MiB against 137 and 222.
  • WinScroll at 1,000–5,000 rows: bough holds 119.7–120.0 presents/s with p95 12.2–13.3 ms; zgx 108.7–111.0 with p95 16.7 ms. BUI reports 138 presents/s at 1,000 rows, above the display’s 120 Hz, because it draws a CPU frame per wheel event without waiting for the display; its counts overstate what was shown.
  • LossDashboard worst gap, the site’s headline: zgx’s worst of three is 42.5 ms against bough’s 75.7 ms (bough’s other runs: 15.3 and 15.1 ms; zgx’s: 32.9 and 42.1 ms). BUI’s worst is 279.8 ms, in a run taken straight after covered-window rejections (its others: 27.2 and 37.4 ms).
  • WinDashboard, the rest: p95 gap 9.2 ms against 25.0 (zgx) and 18.8 (BUI); resident memory 66 MiB against 136 and 171; CPU 2.1 s against 3.6 and 7.1 s.
  • WinExecutable: 2.7 MiB against 5.0 MiB (BUI) and 14.9 MiB (zgx).
  • NoteNot like for like in every respect: zgx draws with its own default font (its ZGX_FONT_FILE is read only by its examples), the others with DejaVu Sans; BUI renders on the CPU on macOS (no GPU renderer there) and is observed through its view’s displayIfNeeded, zgx through its tile flips (verified one record per frame against zgx’s own present log, 319/319). zgx and BUI have far more finished features than bough (accessibility, IME, menus, text editing), which these two workloads do not exercise.

Against every registered framework

Six frameworks are measured on this Mac and twelve are estimated from the site’s Linux numbers (see “Every registered framework”).

  • TiedPresents per second: bough is highest at both 1,000 and 7,000 rows, but every leader sits within about 3 frames of this display’s 120 Hz limit, so on this measure the field is effectively tied.
  • LossSteadiness (p95 gap): iced, measured here, presents more evenly: 8.4–8.6 ms against bough’s 12.4–12.9 ms. Slint was also steadier at 1,000 rows (9.3 ms). bough ranks second of 17 at 7,000 rows and third of 18 at 1,000. bough is observed when it publishes a surface and the others when they take a drawable, so part of the gap may be where the clock is read; it is reported as measured.
  • WinMemory: lowest dashboard resident memory of the 15 frameworks with a value: 66 MiB, against 120 MiB for iced, the next lowest, which was measured.
  • WinExecutable size: smallest of all 18, at 2.7 MiB. The next smallest is egui at about 4.0 MiB, an estimate.
  • Not comparedDashboard worst gap and CPU: the site’s worst gaps are single Linux stalls that do not convert across machines, and its latest collection publishes no CPU time. Among the measured frameworks:
    • bough’s worst dashboard gap was 75.7 ms in the head-to-head run and 39.4 ms in the earlier run;
    • iced’s was 19.0 ms, and egui’s 31.9 ms.
These are not the site’s numbers:
  • bough runs only on macOS (Metal), and the site’s harness is Linux with X11 and MangoHud, so the site cannot list it;
  • everything here was measured on one Mac with a 120 Hz display, against the site’s 144 Hz Linux machine;
  • MangoHud and xdotool were replaced by an injected present observer and macOS events, keeping the site’s schedule and statistics.
What running the workloads exposed in bough:
  • New pieces were needed. Its application surface lacked a scroll container, images and a text input in flow, so div().scroll(..), image and text_input were built for this.
  • Fixed capacities. Its fixed-capacity glyph column overflowed on the dashboard until its capacity was raised.
  • Frames beyond the display. It presents a frame for every input event, about 240 a second in the dashboard, twice what the display can show.
  • No select-all. Its text field has no select-all, so the harness’s “clear the input” step deleted one character.

Each one’s deviations and caveats

zgx. zeronsh/zgx at 0f0a08af (2026-11-11), a fresh clone used by path; crates 0.1.10 with default features. Its docs/getting-started.md was followed in full, including the [patch.crates-io] set it gives an app (zgx’s forks of wgpu-hal, winit and the AccessKit adapters, which the docs say cut Metal command buffers), taken by path from the clone’s vendor/, the same source as the docs’ git patches. Built with a production profile (fat LTO, one codegen unit, stripped), the docs’ dist profile plus strip; no mimalloc feature and no other tuning. The scroll app is a plain scroll() with keyed(..) rows, 960 × 48, padding 12, 14 px black text, alternating colours, not virtualized. The dashboard is written zgx-natively (the spec allows toolkit-native styling) and reaches the toolbar by layout (input at 24, 70; Refresh and toggle to its right). zgx draws in its own default font: its ZGX_FONT_FILE is read only by its examples, so the other apps’ DejaVu Sans file is not used here.

How zgx’s frames were counted. zgx does not take CAMetalLayer drawables. It shows its own IOSurface as a tile of a plain layer and hides the previous tile, once per frame. The observer therefore hooks -[CALayer setHidden:NO] on a hidden layer whose contents are an IOSurface. It was checked against zgx’s own ZGX_PRESENT_LOG: over a 7,000-row scroll the hook recorded 319 tile flips and zgx logged 319 plain-set events, 0.01 to 0.22 ms apart, with no video or drawable path used. The layer’s setContents: calls when zgx allocates a surface (one arrived mid-scroll) are not frames and are excluded for zgx.

BUI. ppmpreetham/BUI at d6be0397 (2026-11-11), GPL-3.0-or-later: Blender’s widget drawing and interaction ported into a C kit with a Rust crate (blenderui 0.5.0, default features, built by path from the clone). It is not Blender and not a general-purpose toolkit: it looks like Blender and follows Blender’s interaction rules. On macOS BUI has no GPU renderer (its GPU renderers are Direct3D 11 and OpenGL 3.3 on Windows and Linux): it draws with its CPU raster into the window’s NSView as a CGImage, once per frame (setNeedsDisplayInRect then displayIfNeeded). That is not a drawable, a GL flush or a published surface, so the observer hooks -[NSView displayIfNeeded] on BUI’s view and stamps it when the call returns. Verified on an animation whose frames the app counted itself: 85–88 renders a second against 85.6 observed records a second. BUI does not wait for the display, so one scrolled frame is handed to AppKit per wheel event whether or not the display can show it (hence 138 presents a second at 1,000 rows against a 120 Hz panel): its “presents per second” counts frames produced, and it overstates what was shown more than the Metal apps’ drawables do.

How BUI’s apps were written. They are the site’s own apps/gpui sources, which BUI’s gpui-compatible syntax accepts, with the crate imported under the name gpui and these changes, all recorded in the files: the div import is dropped (BUI’s prelude supplies it); the root is wrapped in a margin-less <body> of the viewport’s height (BUI’s root is an HTML document with an 8 px body margin that grows with its content, so nothing scrolled without it); in the dashboard the site’s hand-written text input (input.rs, built on gpui’s text system, which BUI lacks) is replaced by BUI’s own input() with the same 360 × 40 box and placeholder, img(path) becomes img().src(path) and the images load from files at run time. BUI’s text is set to the same DejaVu Sans file the other apps use (BUI_FONT). The scroll app has no virtualization; the dashboard mounts all 1,000 records. BUI’s default text colours and the site’s gpui geometry are kept, so its toolbar sits 8 px lower than zgx’s (controls 40 px tall in a 56 px row; input at 24, 78) and the harness’s clicks at (200, 90), (496, 90) and (704, 90) land inside the controls.

Clicks. In the run whose screenshot was taken (in the scroll phase, after the Refresh phase), the Refresh count shown was 480 for zgx and 480 for BUI, equal to the 480 clicks the driver sent in that phase: none was dropped. (bough 467–480 refresh clicks sent per run; zgx 480–480 refresh clicks sent per run; BUI (Blender UI) 480–480 refresh clicks sent per run; bough’s run that was short of its 480 is discussed in the verdict above.) BUI’s window must be activated by a click first (the harness does this); a first click on an inactive window only activates it. Only that one run per app was inspected this way.

BUI’s dashboard worst gap was 27.2, 37.4 and 279.8 ms over its three runs, so its 279.8 ms median-of-max is dominated by one stall. That run was the one taken straight after attempts rejected for a covered window (the window was uncovered when it was accepted); it is reported as measured, not removed.

Both. A rejected run (window covered by another window, as happened to BUI’s 7,000-row run 3 and dashboard runs while another window was in front of the app) was run again, not reported. A first batch for both was discarded because another build ran on the Mac during it, and everything was measured again with the Mac otherwise idle.

How this was measured

Machine
Apple M3 Pro · macOS 15.7.4 · built-in Liquid Retina XDR (ProMotion, 120 Hz). Other work was running; frame pacing is what the window server showed at the time.
Builds
The site’s Vizia apps at its main branch (apps/vizia, and apps/vizia-optimized with Vizia’s rayon feature), --release --locked, Rust 1.97.1, with the harness’s feature selection.
bough
comparisons/bough-awagy, written only with bough’s application surface: flow layout by cephal, div().scroll(..), text, button, image, text_input, routes as methods, Application::run.
Presents
MangoHud does not exist on macOS. An injected library records each frame handed to the window server: a Metal drawable taken (wgpu, GPUI, Skia), an OpenGL flush (egui’s glow), an IOSurface published (bough), a tile of a plain layer shown (zgx: -[CALayer setHidden:NO] on an IOSurface-backed layer), or a view drawn by displayIfNeeded (BUI’s CPU raster). The window and statistics are the site’s frames.py rules: anchored on a frame, gaps from the previous frame, the trailing silence counted, ceiling-index percentiles.
Input
The harness’s schedule as macOS events. The pointer is moved over the window and wheel and clicks are real pointer input, routed by the window server, as XTest’s are on Linux. Keys are posted to the app’s process only, so they can never land in another app. Each app was activated, and runs whose window became covered were rejected.
Memory and CPU
proc_pid_rusage: resident memory (the site’s RSS), plus macOS’s physical footprint, which also counts the GPU driver’s memory; CPU time inside the measured window.
